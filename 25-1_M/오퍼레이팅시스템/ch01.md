# 1. Computer System Overview I
"OS의 또 다른 이름: **자원 관리자**"
> 대략적인 흐름: HW 용어 파악 - OS 발달 역사
## 컴퓨터의 기본 구성 요소
- 프로세서(또는 CPU): 프로그램을 실행하는 장치
- 메모리: 데이터와 프로그램(명령어 집합)을 저장하는 장치. 휘발성
- I/O 모듈: 컴퓨터와 사용자 사이에서 데이터를 이동시키는 장치
  - CPU, 메모리 제외 나머지가 여기에 해당(디스크, 그래픽카드 등)

이들은 **버스**라는 물리적 통로로 서로 연결되어 있음
## 프로그램의 실행 과정
### 프로그램과 프로세스의 차이
- 프로그램: 특정 작업을 수행하기 위한 명령어 집합
- 프로세스: 메모리에 적재된 프로그램. CPU에 의해 실행될 수 있는 상태
### 프로그램의 변화 과정
1. 소스 코드
   - 컴파일 결과 기계어로 변환
2. 기계어
   - 기계어와 명령을 1대1로 대응한 것 - 어셈블리어(아키텍처마다 다른 형태)
   - 기계어로 컴파일된 프로그램은 디스크에 저장
   > [참고] 리눅스 계열 OS: 컴파일된 프로그램을 .elf 포맷으로 저장
### 컴퓨터 부팅 과정
1. 컴퓨터 전원 들어옴
2. 디스크의 퍼스트 블록(리눅스 - 부트 블록)에서 로더 실행
3. 로더에 의해 메모리에 OS 적재
4. 이제 컴퓨터는 OS에 의해 관리되는 상태
### 프로그램 실행 과정
1. 프로그램 실행 트리거(GUI 기반 OS의 경우 아이콘을 클릭하는 행위)
2. OS가 메모리에 프로그램 적재(디스크에서 복사)
   - 즉 디스크에 있던 프로그램이 OS에 의해 메모리 내에서 프로세스가 되어 CPU에 의해 실행될 수 있음
3. CPU가 프로세스의 명령어를 하나하나씩 수행

## 프로세서(CPU)의 구성 요소 및 작동 과정
자세한 내용은 컴퓨터구조론 과목 통해 공부 추천
### 구성 요소
- ALU(Arithmetic/Logic Unit)
  - 산술 연산(사칙연산) 및 논리 연산(참거짓, 불 대수)을 수행하는 장치
- 레지스터
  - 프로세서 내에서 사용하는 저장 공간
  - PC(Program Counter): 다음에 수행할 명령어의 **주소**를 저장하는 레지스터
  - IR(Instruction Register): 현재 수행할 명령어를 저장하는 레지스터
### 작동 과정
프로세스가 한 명령어를 실행하는 과정을 **Instruction Cycle**이라고 함
1. fetch
   - fetch의 사전적 의미: 반입하다
   - PC가 가리키는 메모리 주소로부터 명령어를 IR에 적재
2. decode
   - IR에 저장된 명령어의 의미를 파악하기 위한 처리(해석) 단계
3. execute
    - 해석한 명령을 ALU를 통해 실행하는 단계
## 프로세서의 발달(진화) 과정
- **bandwidth**(메모리에 대한 데이터 I/O 처리량)이 증가하는 방향으로 발전 
  - 8비트 프로세서란? 메모리 주소도 8비트, 레지스터도 8비트(즉 한번에 처리할 수 있는 정보량이 증가)
- **clock speed**(단위시간당 명령어 실행횟수)가 높아지는 방향으로 발전
> 성능이 좋아지는 만큼 전력소모, 내부 설계 복잡도, 발열이 함께 증가하는 문제 발생
> - 교재 그림 보면 90년대에 절정임을 알 수 있음
- 위의 문제로 인해 2000년대 인텔, AMD 등의 회사에서 멀티코어 프로세서 출시
### 저성능 프로세서
- 예) 8비트 프로세서의 경우 TV 리모콘 등에 사용됨. 프로세서 판매 수량으로만 따지면 64비트보다 더 많음
- ARM 프로세서는 스마트폰 등에 사용됨
### 최근 프로세서 경향 - SoC(System on Chip)
옛날에는 하나의 종류로만 확장하는 방식으로 멀티코어를 정의했다면, 요즘은 멀티코어를 이루는 프로세서의 종류가 다양하게 구성
- [참고] 예시: 퀄컴 스냅드래곤 865, 삼성 엑시노스 990 등등
- **big-little solution**
  - 위 예시의 프로세서가 사용하는 아키텍처이며 ARM에서 제시한 솔루션
  - 하나의 빅 코어와 여러 개의 리틀 코어로 구성
  - 빅 코어(big core): 고성능 코어이며, 로드(계산량)-전력 그래프에서 초반에 전력소비량이 크지만 증가폭 기울기가 완만
  - 리틀 코어(little core): 저성능 코어, 로드-전력 그래프에서 초반에 전력소비량이 작지만 증가폭 기울기가 급함
- **dynamic frequency algorithm**(리눅스 진영에서 부르는 이름)
  - 데이터 로드량의 크기에 따라 사용할 코어를 구분하여 동적으로 명령 처리하는 알고리즘
  - 최신 논문에 따르면 해당 알고리즘을 사용할 때 전력 소비량이 30-40% 감소
> #### 분업의 시대 
> - CPU가 범용 목적에 이용되는 한편, GPU는 덧셈 뺄셈 등의 특정한 목적에 최적화됨
> - 인공지능에는 많은 양의 사칙연산이 활용되는데(가중치 계산 등), 이때 GPU를 활용하면 하나의 연산을 대량으로 수행할 수 있어 효율적임
>   - 더 나아가 AI에 최적화된 NPU까지 활용한다면 더 효율적일 것

### 폰 노이만 아키텍처
- 적절한 소프트웨어를 메모리에 올려놓기만 하면 프로세서가 그에 맞게 명령 수행하는 시스템
- 폰 노이만 아키텍처를 이용하면 소프트웨어의 목적에 따라 범용으로 시스템 사용 가능

> 알파고와 이세돌의 대국에서 알파고가 승률은 높았지만 전력소모가 엄청났음
> - 그 원인은 메모리에서 발생하는 병목현상인 **폰노이만 병목**
> - 폰 노이만 구조에서 데이터를 로드 및 처리하기 위해 메모리에 반복적으로 접근하기 때문
> - 인공지능에는 폰 노이만 아키텍처가 어울리지 않음

### 미래 - Neuromorphic Architecture
#### 폰 노이만 병목 해결 방법(제안)
1. 프로세서와 메모리 사이의 버스의 대역폭 확장
2. 프로세서의 구조를 단층이 아닌 복층 구조로 설계

> 1, 2번은 폰 노이만 병목의 본질적인 문제(아키텍처 설계상에서 문제)를 해결하지 못함

3. [중요] 인간의 신경망(뇌구조)을 하드웨어로 구현 - **Neuromorphic Architecture**
- 사람의 효율적인 예측 능력으로부터 힌트를 얻은 아키텍처 방식(패러다임)
- 전력소모 매우 감소(분산 컴퓨팅으로 인한 초저전력)
- 빠른 시일 내에 상용화될 것으로 예상

## 메모리
RAM(Random Access Memory)
- 임의 순서대로 접근 가능(random access)
- 바이트(1 byte = 8 bit) 단위로 정보 저장/처리
- 트랜지스터를 이용해 1비트 기억 소자 구성
  - 구성 방식에 따라 SRAM과 DRAM으로 구분
  - 컴퓨터의 전원이 꺼지면 소자에 저장된 정보가 사라짐 - **휘발성**(volatile)
### SRAM(Static RAM)
**6개의 트랜지스터**를 이용하여 1비트 소자를 구현하는 RAM ← 6T
- 가격 ↑, 부피 ↑, 속도 ↑
- 위의 특성으로 인해 프로세서의 캐시(cache) 메모리로 활용
### DRAM(Dynamic RAM)
**1개의 트랜지스터**와 **1개의 축전기**(capacitor)를 이용해 1비트 소자를 구현하는 RAM ← 1T1C
- (SRAM에 비해) 가격 ↓, 부피 ↓, 속도 ↓
- 위의 특성으로 인해 컴퓨터 시스템의 메모리로 활용

## [참고] Heterogeneous Memory
- 각 프로세서마다 로컬 메모리가 존재하는 경우를 말함
- 명령 실행 중 필요하다면 다른 프로세서의 로컬 메모리에 접근할 수 있음
  - 하지만 둘 사이의 물리적 거리가 멀기에 그 속도는 상대적으로 느림
> ### Cold Start Problem
> - AI를 이용해 연산(학습 등)을 수행할 때 AI 모델을 GPU의 로컬 메모리에 로드해야 하는데, 
> AI의 모델이 점점 커져 메모리에 로드하는 시간이 길어지는 문제를 의미
### CXL(Compute Express Link) Memory
- AI 이용시 메모리 부족 문제를 해결하기 위해 고안된 메모리 표준
  - 아직 상용화는 안 됐으나 곧 될 것 같다고 추측
- **PCI 인터페이스**에 메모리를 꽂아도 로컬 메모리인 것처럼 인식되고 동작하는 것
- (같은 메모리를 사용하더라도) 장착한 슬롯이 다르면 연결된 버스가 다르므로 메모리 동작 속도에 차이 발생
  - 계층화된 메모리 구조(Tiered Memory)라고 함
  > 자주 접근하는 데이터(hot data)를 높은 계층인 DRAM에, 
  > 상대적으로 덜 자주 접근하는 데이터(cold data)를 낮은 계층인 CXL 메모리에 저장하면 효율적
## Hard Disk Drive(HDD)
- 비휘발성 저장 장치(I/O 모듈)
  - 자기장의 방향으로 정보를 표현하기 때문에 컴퓨터의 전원이 꺼져도 정보(자기장 방향)가 유지
- 읽고 쓰기 위헤 헤드가 물리적으로 움직여야 함
  - 헤드가 돌아가는 시간(seek time)은 ms 단위(1 ms = 10^-3초)
  - 충격에 매우 약함 → PC, 서버에 주로 사용
## 플래시 메모리(Flash Memory)
- 트랜지스터 구조로 중간의 플로팅 게이트(floating gate)를 제외한 외부가 절연체로 구성
- 플로팅 게이트에 전자를 주입(injection, program)해 정보 저장
  - 외부가 절연체이므로 전자가 빠져나가지 못해 **비휘발성** 저장 장치
  - 속도: HDD < 플래시 메모리(us 단위. 1 us = 10^-6초) < RAM
- **R/W 비대칭성**: 읽기에 비해 쓰기 속도가 현저히 느림
  > OS 입장에서 플래시 메모리 쓰기 작업을 최대한 지양해야 함
- **정보 수정의 비효율성** (no in-place update)
  - 특정 블록(저장 단위)에 정보를 수정할 때, 이미 있던 정보를 없애는 과정(클린)이 필수
  - 그래서 다른 블록에 정보를 저장하는 편이 효율적
- 한 블록의 **쓰기 횟수가 제한됨** (약 10만 번 정도의 수명)
  - 여러 블록에 걸쳐 나누어 쓰는 편이 효율적 - **wear leveling**
### SSD(Solid State Disk)
플래시 메모리 기반 저장장치
- **FTL**(Flash Translation Layer)
  - I/O 버스와 메모리 블럭 사이에 존재하는 소프트웨어 계층
  - 운영체제가 SSD를 (플래시 메모리가 아닌) HDD와 같이 취급하도록 인터페이스 제공
<hr/>

> ### 메모리 속도 비교
> - 프로세서 처리 사이클 → 약 0.5 ns
> - 캐시 접근 → 약 2 ns
> - 메모리 접근 → 약 15 ns
> - SSD 접근 → 50000 ns(50 us)
> - 디스크(HDD) 접근 → 7000000 ns(7 ms)

## 레지스터
프로세서 내에 존재하는 명령어 처리 중간 결과 저장용 메모리

### 범용 목적 레지스터
- 명령어 처리 도중의 중간 결과를 저장
- 개발자는 레지스터 사용을 통해 메모리 참조 최소화 가능

### 특수 목적 레지스터
OS 개발사(벤더)마다 이름이 다를수도 있음
- PC(Program Counter)
  - 다음에 fetch될 명령어의 주소값 저장
- IR(Instruction Register)
  - 현재 fetch된 명령어의 내용을 저장
- PSW(Program Status Word)
  - 최근 명령어를 실행한 후 시스템의 상태(컨디션 코드라고 함)를 저장
  - CPU의 현재 상태, 연산 상태(오버플로우, 값이 0인지, privilege level 등 등) 확인 가능
  - [참고] privilege level: 지금 실행한 연산이 OS의 내용인지, 어플리케이션 프로세스의 내용인지 여부
> CPU와 메모리 간 통신시 이용하는 레지스터 → MAR, MBR
> - 이 둘이 CPU와 메모리 간 인터페이스가 됨
> - 명령어 한 줄 실행을 위한 fetch 과정에서도 MAR과 MBR이 중간에 이용됨
>   - PC 주소 참조 → MAR에 저장 → (MAR 내 주소에 있는)메모리에서 로드 → MBR에 저장 → MBR의 내용 IR에 저장
> - CPU와 I/O 간 통신시에도 I/0 MAR, I/O MBR 이용
- MAR(Memory Access Register)
  - 다음에 읽고 쓸 메모리 주소값을 임시로 저장
  - PC와 다른 점: PC는 명령어 fetch를 위해 주소값을 저장하지만 MAR은 단지 메모리 접근을 위해 메모리 주소를 저장
- MBR(Memory Buffer Register)
  - 메모리에 쓰려는, 메모리로부터 가져온 데이터 임시 저장하는 용도
  - MAR에 저장된 주소에 해당하는 메모리의 데이터값을 저장

## 명령어 집합 구조(Instruction Set Architecture - ISA)
- 소프트웨어와 하드웨어 사이의 인터페이스를 정의
  - 명령어와 machine states(레지스터와 메모리의 상태 변화)를 정의
  > - ADT(추상 데이터 타입)와 비슷: ADT도 동작과 그 결과만을 정의한 명세이며, ADT를 어떻게 구현하든 상관 없음 
  > - ISA 또한, 이 명령어를 사용하면 레지스터와 메모리가 이렇게 변한다~ 를 명시한 것으로, ADT와 마찬가지로 어떤 과정을 거쳤는지는 상관이 없음
- 예: x86, AMD64(x86-64), IA64, ARM

인텔의 프로세서인 펜티엄과 펜티엄 프로 모두 x86 아키텍처를 따르기 때문에 서로 명령어가 호환되지만, 명령어 구현 방식이 다르므로 성능에 차이가 존재
## 명령어 포맷
특정 기계에만 해당되는 명령어 템플릿을 정의한 것으로, 명령어 포맷은 아래의 두 가지 요소로 구성
- Opcode(연산자)
  - 수행해야 할 연산을 정의한 것
  - 인텔 아키텍처 예: mov, add, jump 등
- Operands(피연산자)
  - 메모리에 대해 읽고 쓸 데이터 또는 메모리 주소를 표현
> 명령어 포맷의 형태는 고정 길이이든, 가변 길이이든 명확히 정의만 되면 상관 없음
### [예시] 교재 저자가 정의한 명령어 포맷
- 16비트의 명령어 포맷 존재
- 비트의 상대적 위치가 0 - 3인 경우 opcode, 4 - 15인 경우 operands
  - 예: 0001 - 메모리로부터 정보를 로드, 0101 - 메모리로부터 합을 구해라

### 명령어의 성격(종류)
1. 데이터 간 연산(Data Processing) - 더하기 빼기 같은 값 계산
2. 명령어 실행 흐름 제어 - 프로시저 콜(함수 호출), 시스템 콜 등
3. 프로세서 와 메모리 간 통신 - 로드, 저장
   - ex: mov
4. 프로세서와 I/0 간 통신
   - 인텔 기준: in, out
> #### 헷갈리지 말기
> ISA가 변화시키는건 메모리와 레지스터의 상태이지, 캐시가 아님
> - 캐시는 퍼포먼스를 위한 영역

## 인터럽트(Interrupt)
### 인터럽트의 필요성
- CPU는 스스로 판단하지 않고 정해진 명령어만 절차대로 처리
- 프로세스의 내용과는 상관 없이, CPU는 명령어 처리가 시작된 프로세스를 끝까지 절차대로 처리해야만 함
  - 설령 프로세스가 시스템 자원을 독점하더라도 마찬가지
- 위의 상황을 막기 위해, OS가 프로세스 실행에 개입할 방법으로서 인터럽트가 필요함

### 인터럽트 메커니즘
- 하드웨어에 의해 발생하는 이벤트를 인터럽트라고 함
  - 인터럽트 종류를 구분하기 위해 책에서는 'IRQ(Interrupt Request) n'으로 표기
  - 이때 n을 인터럽트 벡터(Interrupt Vector)라고 함
- 인터럽트 발생시 현재 실행중인 프로세스 중단
  - 이후 적절한 Interrupt Handler(중요: **OS 코드의 일부**)를 호출해 처리
- 핸들러 통해 인터럽트 처리 후 원래 실행하던 프로세스의 명령어 (다음)위치로 돌아와야 함
> - 인터럽트가 발생해도 CPU는 쉬지 않음
>   - 실행하는 명령어 종류가 유저 코드(프로세스)에서 OS 코드(인터럽트 핸들러)로 변경되었을 뿐
> - CPU가 한 명령어를 처리하고 나서 발생한 인터럽트 있는지 확인
>   - 있으면 핸들러 수행해 인터럽트 처리하고 없으면 다음 명령어 재개

#### 인터럽트 메커니즘의 장점
1. Timely Service
> - 인터럽트를 통해 시간에 의존하는 이벤트를 빠르게 처리 가능
> - 컴퓨터 시스템 내 시간 관련 I/O 장치 통해 timely service 수행 가능
> 시간 관련 I/O 장치
> 1. 시스템 타이머
> - 부팅 이후에 흐른 시간을 틱을 발생시켜 상대 시간 계산, 상대 시간은 volatile
> - 틱의 해상도란 초당 틱 발생 횟수이며, 보통 초당 1000번(횟수를 해상도라고 함) 틱 유발
> - 틱 유발할 때마다 인터럽트 발생
> - 자원 관리할 때 상대 시간 이용
> 2. 리얼 타임 클락
> - 특정 시점을 기준으로 현까지 흐른 절대 시간을 계산
>   - 절대 시간 정보는 없어지면 안되므로 non-volatile한 특성을 띰
>   - 정보를 보존하기 위해 메인보드의 코인 배터리를 이용
> - 파일 저장 시간 등의 정보에 절대 시간 이용
2. System Utilization
- 컴퓨터 시스템이 불필요하게 쉬지 않고 효율적으로 명령 처리해 System Utilization이 높아짐
> #### [참고] DMA 컨트롤러
> - CPU 대신 I/O 작업을 요청, 처리하는 주체
> - 폴링(I/O의 상태를 수시로 확인하는 것) 통해 I/O 유휴인지 확인 후 작업 수행하는 방식은 System Utilization이 낮음
> - 계속 폴링하는 대신 다른 유의미한 작업(프로세스 처리 등)을 하는게 CPU에선 이득
3. 자원 독점 방지
- 인터럽트 필요성 부분에서 설명했음

### I/O 장치(devices) 구성
디스크를 예를 들어 설명
1. **구현체**: 좁은 의미의 I/O 장치로서 실제 작업을 수행하는 **기계 본체**를 말함
2. 제어 파트(interfaces): 구현체를 제어하기 위한 역할
- 레지스터
  - 상태 레지스터: busy/idle/error 3가지 상태로 I/O 장치 상태 구분
  - 컨트롤 레지스터: read/write 명령
  - 데이터 레지스터: r/w 작업을 어느 위치에 수행할 것인지(write의 경우 그 값까지) 저장
- 로컬 버퍼: 디스크의 경우 취급하는 데이터 용량이 크기 때문에 필요
- 로컬 램
- **I/O 컨트롤러**: I/O 디바이스의 프로세서이며 시스템의 CPU와 직접 통신하는 주체

### 인터럽트 제어기(PIC)
- 인터럽트 메커니즘에 필요한 별도의 하드웨어
- IRQ Controller라고도 하는 듯

#### PIC의 두 가지 역할
1. **translation**
- 다양한 I/O 디바이스와 맵핑해 인터럽트 종류를 구분하는 중개자의 역할
  - I/O 디바이스와 CPU는 핀을 통해 연결되는 구조
  - 그러나 CPU의 핀 개수는 유한하므로 I/O 디바이스 연결에 한계
  - 이를 PIC가 해결함과 동시에 각 인터럽트를 구분해 CPU에 인터럽트 요청 전달(예: IRQ n과 같은 정보와 함께)
> PIC의 핀에 PIC를 추가로 연결해 더 많은 I/O와 연결 가능
2. **masking**(비활성화하는 것)
- PIC의 P는 programmable(활성화/비활성화 가능) → PIC의 인터럽트 맵핑 기능을 온오프 가능
- 즉 인터럽트 핸들러 수행 중에 발생한 다른 인터럽트를 바로 처리할지, 대기시키고 현재 핸들러 끝나면 처리할지 결정 가능

### 인터럽트 핸들러와 인터럽트 서비스 루틴(ISR)
- 인터럽트 핸들러와 인터럽트 서비스 루틴 모두 인터럽트를 처리하는 데 사용됨
- 인터럽트 핸들러는 인터럽트 처리시 **공통적으로** 실행하는 명령을 의미할 때 사용하는 용어
  - 리눅스 환경의 경우 커널 내의 어셈블리 파일 entry.s가 이에 해당하며 공통적으로 saveAll(레지스터 정보 저장), restoreAll(저장한 레지스터 정보 복원) 처리
- ISR은 **특정 디바이스와 관련된** 인터럽트 처리 명령을 강조할 때 사용하는 용어
  - 리눅스 환경의 경우 시스템 타이머와 관련된 timer_interrupt()가 ISR에 해당
  - entry.s 실제 내용: C언어 함수 do_IRQ(n)를 호출한 뒤 인수 n에 해당하는 IDT 테이블의 요소에 접근하여 적절한 ISR 실행
  - **IDT 테이블**: 인터럽트 벡터와 이에 대응되는 ISR을 함수 포인터 형태로 저장한 테이블
### 인터럽트 처리 과정
1~5번 및 9번은 하드웨어적으로 처리, 6~8은 소프트웨어적으로(핸들러 통해) 처리
1. I/O 인터럽트 발생
- I/O와 CPU 사이에 존재하는 PIC가 인터럽트 확인 후 CPU로 인터럽트 요청을 전달
2. 명령어 처리(execute)를 완료한 뒤 인터럽트 발생 여부 확인
- 인터럽트 요청 존재시 현재 프로세스 실행 중단, 없으면 프로세스 재개
3. CPU가 PIC에게 응답 시그널(대충 인터럽트 인지했단 의미) 전송
4. PC와 PSW 값을 제어 스택에 저장
- 인터럽트 처리시 두 레지스터 모두 수정되므로 처리 후 원상복귀 위해 값 저장
- 스택에 저장하므로 CPU 내 스택의 TOP 주소를 가리키는 레지스터인 스택 포인터 또한 업데이트
5. PC를 인터럽트 핸들러의 시작 주소로 업데이트(제어: 유저 코드 → OS 코드)
> CPU는 자기 할 일 묵묵히 하며 인터럽트 핸들러 실행. 아래는 핸들러의 내용
6. saveAll: 프로세스와 관련된 나머지 정보(레지스터 값) 스택에 저장
7. 인터럽트 처리 - ISR 통해
8. restoreAll: 6번 과정에서 저장했던 프로세스 관련 정보 복원
9. PSW와 PC 복원

## 예외(Exception)
넓은 의미의 인터럽트는 명령어 실행 도중에 발생한 모든 이벤트를 포함하지만, 이벤트 발생 위치에 따라 두 가지로 구분 가능
- '좁은 의미의' 인터럽트: CPU 외부에서 발생한 이벤트
  - PIC에 의해 전달받음
  - 인터럽트 발생 자체는 CPU 클럭과는 비동기적으로 발생
  - 하지만 CPU 명령어 사이클이 끝난 이후에 확인/처리
- **예외**: CPU 내부에서 명령을 처리하다 발생한 이벤트
  - 잘못된 메모리 주소에 액세스, 잘못된 op코드, 0으로 나누는 명령 등
  - 인터럽트와 비슷하게, 각 예외 상황에 대응되는 핸들러를 선택해 예외 처리
  - 정의에 나온 것처럼 명령어 사이클 도중에 발생하며 CPU 클럭과 동기적으로 발생

## I/O 요청 처리 비교
I/O 장치에 값을 저장하는 write 명령 수행 과정 비교
### 1) 인터럽트 X
> 디바이스 드라이버
> - OS 코드의 일부로서 I/O 컨트롤러에 전달할 명령을 세팅하는 역할
> - I/O 벤더가 정의한 인터페이스 역할
> I/O 커맨드
> - CPU 개입이 끝나고 I/O 모듈이 자체적으로 작업 수행하는 것

1. 프로세스 내에서 write 명령 실행
2. OS 코드로의 모드 스위치 발생으로 I/O 프로그램 수행
3. I/O 커맨드 단계가 끝날때까지 CPU 대기(idle)
3. I/O 수행 결과를 CPU가 획득
### 2) 인터럽트 O(I/O 수행시간 짧은 경우)
1. write 명령 의해 모드 스위치 발생
2. I/O 프로그램 통해 setup
3. I/O 커맨드 수행시 CPU가 원래 프로세스의 작업을 마저 수행
4. I/O 커맨드 끝나면 발생하는 인터럽트에 의해 **프로그램 수행 도중** 모드 스위치
5. 인터럽트 처리 후 복귀
### 2) 인터럽트 O(I/O 수행시간 긴 경우)
짧은 경우보다 인터럽트가 느리게 발생
1. 인터럽트 대기 도중 write 명령을 수행해야 하는 경우 발생
2. 두 번째 write 명령 **대기**시키고 인터럽트 처리
- 대기하지 않으면 아까 진행한 I/O 작업에 영향을 주므로 소프트웨어에서 막아야 함
3. 이후 두 번째 write 명령 처리

> ### 메모
> - I/O 처리시간이 길더라도 인터럽트 메커니즘 없이 처리하는 것보단 시간적 측면에서 이득
> - 펌웨어의 경우 I/O 대기시간이 짧을 때 인터럽트를 미사용하기도 함
>   - 구현이 간단하므로 

## 인터럽트 처리 중에 인터럽트 발생한 경우
1. Sequential Interrupt Processing
- 나중에 발생한 인터럽트를 대기시킨 다음(pending) 현재 인터럽트 처리 후 대기했던 인터럽트 처리
- 단순한 방식이므로 구현하기 쉬움
- 시간 긴급도(빨리 처리해야 하는 인터럽트 존재)를 고려하지 않음
  - 차량용 OS, 우주선 같은 분야에선 사용 불가
2. Nested Interrupt Processing
- 인터럽트에 존재하는 우선순위에 따라 인터럽트 처리
- 인터럽트 처리 도중 현재 인터럽트보다 더 중요한 인터럽트가 발생한 경우, 더 중요한 인터럽트 먼저 처리
- 스택을 통해 구현할 수 있음
- 구현이 다소 복잡하나 시간 긴급도를 고려한 작동이 가능하다는 장점 존재
