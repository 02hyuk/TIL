# OS - 3주차(2)
## OS의 3가지 특징

서비스 제공 → **편리성**

- 프로그램 개발 및 실행
- 프로세스 및 메모리 관리
- 파일 관리(접근 제어)
- 하드웨어 관리
    - 사용자가 하드웨어 상세 정보를 몰라도 조작 가능하도록 인터페이스 제공 - **API**(ISA를 고수준 프로그래밍 언어로 이용할 수 있게 하는 수단)**, ABI**(같은 OS의 실행 파일 표준 느낌)
- 등등

하드웨어 자원 관리 → **효율성**

- 각 하드웨어에 대한 메타데이터 통해 효율적으로 관리
    - CPU - 프로세스 단위로 처리 단위 추상화
    - 메모리 - 프레임 단위로 메모리 관리. 보통 4KB
        - 페이지: 프로세스를 조각내어 관리하는 단위. 보통 4KB
        - 페이지 테이블: 각 프로세스마다 존재하는 메타데이터로 프로세스의 페이지와 메모리의 프레임 사이의 맵핑 정보를 저장
    - 파일 - 블럭
        - I-Node: 파일의 블럭과 디스크의 섹터에 대한 맵핑 정보
- UNIX 계열 OS는 위에서 언급한 메타데이터를 C언어 구조체 형태로 관리

> OS는 일반 소프트웨어처럼 CPU에 의해 수행되는 프로그램이며, 제어(처리기 사용 권한)를 양보하거나 돌려받는 것도 CPU에 의존한다는 **수동적인 특성**을 가짐. 하지만 이것은 **OS의 의도** 하에 동작하는 것임
>

**발전 가능**

- OS는 서비스 제공에 방해받지 않고 새롭게 발전할 수 있는 구조를 지녀야 함 → 서비스 제공과 진화는 병행적
    - 발전의 이유: HW 업그레이드 및 새 HW 등장, 새로운 서비스 등장, 버그 수정 등

## 1) Serial Processing(순차처리)

사용자가 컴퓨터에 순차적으로(serial) 접근해 처리하는 방식

> 당시 성능 지표 - **CPU 이용률(CPU Utilization)**:  단위 시간 동안 CPU 자원의 사용 시간
>

당시 컴퓨터 시스템

- 값비싼 물건이라 정부가 관리 진행
- OS가 없어 사람이 OS 역할을  대신함(**human operator**)
    - job(=작업. 현재의 프로세스와 비슷한 의미)을 받아 사람이 직접 컴퓨터에 입력한 뒤 연산 결과를 받아 전달 → 그래서 job 간 전환(**job to job transition**)이 굉장히 느림
    - 당시에는 고수준 언어 및 어셈블리 코드를 **카드 형태**로 작성 → **컴파일** 과정도 사람이 진행
- 사람들이 자주 사용하는 소프트웨어()를 공유하기 시작 → **라이브러리** 개념 등장

순차 처리의 문제점 - 값비싼 자원의 **비효율적 사용**

- 인간의 개입으로 인한 job 간 전환이 느렸음
    - **high setup time**
        - job sequencing(job들의 실행 순서를 결정하는 것) 과정이 **수동**으로 진행
        - job 수행 또는 전환 위해 카드나 전선을 **직접 꽂고 빼는 과정**들
    - **scheduling time**: 각 job에 대한 할당 시간을 적절히 배치하기 어려움(프로세스의 정확한 수행 시간을 계산하는 것은 현대에도 어려움)

  > 프로세스의 수행 시간이 스케줄링 타임을 넘게 될 경우엔 이전까지의 연산 결과가 버려지고, 반대로 시간이 남았을 경우엔 컴퓨터가 아무 것도 못하고 남은 시간 동안 가만히 있어야 함

## 2) Simple Batch System(단순 일괄처리 시스템)

> 당시 성능 지표 - **처리량(Throughput)**: 단위 시간 동안 처리된 프로세스(job)의 수

### 시스템의 목표

- job to job 전환 과정을 자동화 - **automatic job sequencing**
- job들을 하나로 묶어 컴퓨터 이용 전 설정 시간을 줄이자(설정 과정까지 자동화) - **Reduce setup time**

### **배치 모니터**(Batch Monitor) - 거의 최초의 OS

- 자동화 과정에서 **모니터 동작 제어** 수단 필요 → **JCL(Job Control Language)**: job에 대한 시퀀싱(실행 순서 결정), 컴파일, 실행, 전환 등의 명령이 담긴 프로그래밍 언어
- 다른 이름은 **Resident Monitor** - job 관리 과정이 자동으로 계속 진행되어야 하므로 모니터가 **메모리에 상주**하도록 함(resident)

→ OS와 사용자 프로그램의 영역 구분이 이때부터 시작됨

### Simple Batch System의 자원 보호

**CPU 보호**

- (무한 루프 등을 통한)특정 job의 CPU 독점 방지 → 시스템 타이머로 **실행시간 측정**
- 시스템에 중대한 영향을 줄 수 있는 **특정 명령**(시스템 중단 등)**은 모니터만이 수행** 가능하도록 제한

**메모리 보호**

- **모니터가 메모리에 상주**
- 사용자 프로그램의 **커널 영역 침범 제한**
    - 커널 영역 침범 시도 → **예외 발생**(segmentation fault)
    - 메모리에 적재된 job은 자신에게 할당된 범위에만 접근 가능

**I/O 보호**

- 사용자 프로그램에서 I/O 명령 사용시 **모니터를 거쳐 요청**해야 함 → **System Call**의 형태
    - **privileged instruction**(특권 명령어): 모니터만이 수행 가능한 명령어. I/O 명령이 여기에 속함

### CPU의 실행 모드

1. **user mode**
    - 제한된 권한을 제공, 사용자 프로그램을 수행하는 모드
2. **kernel mode**
    - 모든 권한을 제공, OS의 기능을 수행하는 모드

**mode bit**: 시스템이 사용자 모드인지 커널 모드인지 표시하는 PSW 내의 비트. 커널에 의해 수정됨

**mode switch**: 컴퓨터 실행 중에 어떠한 원인에 의해 실행 모드가 전환되는 것(사용자 ↔ 커널)

- 예) 사용자 모드에서 명령어 수행 중 예외 발생 → 커널 모드로 전환해 예외 처리

> 모드 스위치 또한 모니터만이 수행할 수 있는 특권 명령
>

CPU의 실행 모드를 두 가지로 분류한 이유 → **시스템 보호**

- 위의 자원 보호 측면 단락이 위의 내용과 연관됨

### Simple Batch System의 한계

1. 입출력 장치의 처리 속도가 CPU에 비해 매우 느림
    - 카드 리더기가 천공 카드(데이터)를 읽는 속도, 파일에 데이터를 쓰는 속도
2. (카드 리더기 포함)입출력 장치와 CPU의 작동 시간대가 겹치지 않음 → **CPU가 idle한 시간이 많았음**
    - 어느 정도 겹쳐야 job을 더 빨리 완료할 수 있음
