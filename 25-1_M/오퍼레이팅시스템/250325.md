## 3) Multi-programmed Batch System

job에 입출력 실행 명령이 있을 때 CPU가 입출력 명령을 기다리는 동안 메모리에 적재된 다른 job을 수행 → **CPU 이용률 향상**

- **active job**: 메모리에 적재된 job으로 CPU에 의해 실행될 수 있는 상태

**멀티(다중) 프로그래밍 정도**(multi-programming degree): 메모리에 올라간 job의 수

- 멀티 프로그래밍 정도 증가시 CPU 이용률이 계속 증가하다가 **급격히 떨어지는 시점** 존재
    - 전체 job 용량이 메모리 용량보다 커질 경우 → job 스와핑이 발생해 CPU 이용률 급감소
    - 스와핑(swapping): (사용 빈도 등의 이유로)메모리에 있는 job과 디스크에 있는 job의 위치를 서로 바꾸는 것

**스케줄링**(scheduling)

- 현재 실행중인 job에서 (I/O 등의 이유로) CPU가 대기할 때, 어떤 active job을 실행할지 결정하는 것
- 스케줄링 알고리즘 통해 결정 가능
- [참고] 선택한 job에 따라 시스템 성능이 달라짐

멀티 프로그래밍, 멀티 프로세싱 이 두 단어는 혼용해서 쓰이긴 하나 같은 개념은 아님

- 멀티 프로그래밍: 메모리에 여러 프로그램을 적재한 것
- 멀티 프로세싱: CPU가 여러 프로그램을 처리하는 것

> 유니(단일) 프로그래밍(uni-programming) 시스템에서 job을 수행하는 중간에 다른 job을 메모리에 대신 적재해 병행해서 실행하면 단일 프로그래밍이자 멀티 프로세싱
>

### 멀티 프로그래밍 시스템의 문제

1. 주소 재배치 문제(**relocation**)
    - 유니 프로그래밍: 메모리에 OS와 1개의 프로세스 → 메모리 로딩 시점에 **프로세스 시작 주소 예측 가능**
    - 멀티 프로그래밍
        - 런타임에 job의 시작 주소가 **동적**으로 정해짐
            - 시작 주소 예측하기 어려움(현대에도 마찬가지)
            - job에서 주소 연산할 때 문제 발생
        - 잡 스와핑에 의해 퇴출 후 다시 적재된 job의 실제 메모리 위치가 이전과 다를 수 있음
2. 메모리 보호 문제(**memory protection**)
    - OS와 사용자 프로그램 영역 뿐만 아니라, 각 job간 영역까지도 침범하면 안됨

### 해결법 - **MMU**(Memory Management Unit)

상대 주소를 물리 주소로 변환하여 프로세스의 메모리를 관리하는 방식

> 아래 베이스, 바운드 레지스터 모두 MMU 안에 존재
>
- OS가 각 프로세스의 **물리적 시작 주소**를 관리
    - **base register**: 프로세스의 시작 주소를 저장
- 사용자 프로그램에서는 상대 주소(0부터 시작하는 논리적 주소) 사용 - 개발자 입장에서 메모리에 적재되는 위치를 모르기 때문
- **bound register**(limit register): 프로세스의 **최대 크기**
    - 베이스 + 상대주소 ≤ 베이스 + 바운드 → 프로세스의 실제 주소 접근
    - 상대주소 ≤ 바운드지 뭐..

현대에도 MMU가 이용되고 있지만 조금 다름

- 프로세스를 페이지 단위로 분할 후 메모리에 적재하기 때문
- 그래서 베이스 레지스터 대신 **페이지 테이블**을 이용

## 4) Time Sharing System

### - 등장 배경

집적 회로(Integrated Circuit - IC) 등장으로 컴퓨터 가격 하락(무어의 법칙)

1960년대 터미널 등장 → 수행 결과 확인을 위해 컴퓨터 있는 곳까지 가지 않고 터미널 통해 빠르고 편하게 확인

- **터미널**(terminal): 모니터, 마우스 등의 장비를 통해 컴퓨터와 상호작용하도록 연결하는 하드웨어 장치

위의 두 가지 이유로 **인간의 노동 가치 상승** → 많은 사람이 효율적으로 이용 원했음(생산성 향상)

- 하지만 당시의 컴퓨터는 (가격이 줄어들긴 했지만) 개인이 소유하기에는 비싼 자원이라 시스템과의 상호작용(대화) 어려웠음
- 그래서 시분할(Time Sharing) 시스템이 등장

### - 목표 및 특징

목표

- 다수의 사용자가 시스템을 동시에 사용하도록 지원하여 사람들의 생산성 증대 도움

특징

- 터미널 통해 다수의 사용자가 동시 접근 가능
    - 다수의 대화형 작업 처리
- 사용자가 **혼자서 사용하는 느낌** 제공 → 나 혼자서 상호작용하는 것처럼
    - 사실 n명이 터미널을 통해 하나의 컴퓨터 사용할 때 각자가 사용하는 성능은 이론상 1/n
    - 하지만 시스템의 반응 시간보다도 우리의 반응 시간이 더 느림 → 시스템의 100% 능력을 사용하는 것처럼 느껴짐
- **Time slicing**(시간 분할) → 각 사용자에게 할당된 시스템 사용 시간
    - 시스템이 주기적으로 타이머 인터럽트 발생
    - 인터럽트 발생시 CPU 제어가 다른 프로세스로 전환됨
        - 보통 round robin 전략으로 전환
    - 선점(preemption): CPU에 의해 현재 실행되던 job이 **타의적으로** CPU 실행 권한을 반납하게 되는 것
        - 즉 타이머 인터럽트 발생시 선점 발생
    - 프로세서가 1개였던 당시 사용자를 구분해 서비스를 제공할 방법은 시간 분할이 유일했음

### - 시스템 타이머(System Timer)

시간 측정을 위해 주기적으로 인터럽트를 유발하는 하드웨어

- 핸들러(OS코드) → tick이라는 전역변수 1 증가, 현재 실행중인 프로세스의 실행시간 또한 1 증가
- 만약 프로세스가 타임 슬라이스만큼 시간 썼다면? → 선점 후 프로세스 변경

### - 시분할 시스템의 성능상 이점

멀티 프로그래밍 시스템의 경우 입출력 명령이 없으면 한 프로세스를 계속 실행하게 됨 → 다른 프로세스가 시작을 못하므로 응답 시간이 길어짐

하지만 시분할 시스템을 활용하면 정해진 시간만큼 프로세스를 실행하므로 다음 프로세스 처리 시작 시간이 앞으로 당겨짐 → **응답시간 감소**

의도하진 않았지만 응답 시간이 감소하면서 CPU 이용률이 좋아지는 결과가 따라옴

> [당시의 성능 지표]

**응답 시간(Response Time)**: 프로세스가 시작된 때부터 응답이 시작될 때까지의(첫 번째 응답이 도착하기까지의) 시간

**반환 시간(Turnaround Time, TAT)**: 프로세스가 시작된 때부터 응답이 시작될 때까지의(첫 번째 응답이 도착하기까지의) 시간
>

### - 이야깃거리

Multics라는 최초의 시분할 OS가 등장

- 최초로 프로세스라는 용어 사용
- 이후 UNIX 등의 OS에 큰 영향

UNIX 출시

- 웬만한 시스템과 호환 가능했음

시분할 시스템 이용 과정에서 다양한 문제 제기

1. 프로세스 스위치가 굉장히 많아짐 - 오버헤드 증가
    - 그럼에도 효율적이긴 함
2. 서로 다른 job간 간섭 방지 필요
3. 파일에 대한 보안 문제
    - 파일 시스템 - 접근 제어, 권한 관리 등의 기능 필요
4. 데이터 동기화 문제
    - 두 프로세스가 동일한 데이터에 접근해 연산하는 중간에 선점 발생시 데이터의 유효성이 훼손될 수 있음
    - 예: 연산 후 미반영 → 나중 연산에 잘못된 값 참조
    - 해결 방법 - 세마포어, 스핀락 등(나중에 배울 예정)

## 시스템 콜(System Call)

> 사용자 프로그램이 커널의 서비스를 요청하기 위한 인터페이스
>

시분할 시스템을 기점으로 체계적인 파일 시스템을 포함한 다양한 커널 서비스 등장

커널 서비스가 시스템에서 중요한 서비스인 만큼 사용자가 함부로 사용 못하도록 접근 제한

→ 대신 OS가 제공하는 **시스템 콜**을 이용해 서비스 요청 가능

시스템 콜 작동 과정 → 인터럽트, 예외와 비슷

1. 프로그램에서 시스템 콜 호출시 소프트웨어 인터럽트(**예외**) 발생
2. **핸들러**가 처리하는 과정에서 시스템 콜 내용 수행

> 인터럽트, 예외, 시스템 콜 모두 커널 모드로 동작한다는 특징이 있으나 각각 발생 원인이 다름(인터럽트-하드웨어 이벤트/예외-소프트웨어 이벤트/시스템 콜-필요에 의한 요청)
>

### 시스템 콜의 목표

- 시스템 자원 보호
    - 사용자가 일부러, 실수로 자원에 접근하여 잘못 조작했을 때 시스템에 심각한 영향을 줄 수 있으므로 **OS만이 시스템 자원에 직접 접근**하게 하기 위해
    - 사용자는 시스템 콜을 통해 **간접적**으로 자원에 접근함으로써 시스템 보호 가능
- 신뢰성
    - 자원 보호와 연관되는 목표로 **자원 독점을 막음**으로써 신뢰성 보장
    - 무한 루프, 메모리 독점 등의 문제 방지
- 보안
    - 파일 접근 제한 등의 목표 달성

### 시스템 콜의 특징(디자인 철학)

잘 정의된 약 200가지의 시스템 콜은 아래의 특징을 가짐

- 추상적인 명령어 형태
- 작은 크기의 명령어
- 견고한 구조

시스템 콜을 위와 같이 설계하면 좋은 점

- 보안성: 해커가 침입할 여지(시스템에 대한 공격 지점)를 줄여 보안 정책을 수립하기 좋음
- 이식성: 각 시스템마다 변경해야 하는 부분이 적어져 다양한 시스템에 이식하기 좋음

### 시스템 콜 API

시스템 콜의 종류도 많고 사용할 때 OS에 대한 지식이 필요해 이를 편하게 쓸 수 있는 라이브러리로 만듦

- POSIX API(유닉스, 리눅스, 맥)
- Win32 API(이름만 봐도 윈도우용)
- Java API(JVM에서 쓰임)
- 등등

### 시스템 콜 구분

대충 6가지 범주로 구분 가능

1. 프로세스
2. 스케줄링
3. 프로세스 간 통신
4. 파일 시스템
5. 네트워크(소켓)
6. 기타

### [참고, 예시] 시스템 콜 호출 예시

교재엔 없음 이해하는데 참고만

프로세스가 시스템 콜 통해 “hello, world!”를 출력하는 과정

1. 프로세스 실행 시작
    - 컴파일 전 printf(“hello, world!”);을 수행하기 위해 컴파일 과정에서 아래 3, 4번으로 명령이 나눠짐
2. eax 레지스터(시스템콜 구분 번호 저장하는 레지스터)에 4(쓰기) 저장
    - 을 수행하기 위해 사용자 프로그램을 컴파일하면서 위와 같이 동작
3. (x86 아키텍처 기준) CPU가 int $0x80 실행 → 뭐야 인터럽트네?
    - 어셈블리 코드에는 시스템에 접근하는 코드가 없음. 시스템 콜만 있을 뿐
4. 인터럽트 핸들러가 적절히 처리하기 위해 IDT 탐색 → 0x80(128)번에는 시스템 콜 존재
5. 핸들러가 ENTRY(IDT에 있던 함수포인터 → 여기선 시스템 콜 의미) 실행
    - entry.s에 정의된 인터럽트 처리 함수
    - 현재 상황에선 syscall.c에 정의된 함수 포인터 테이블 sys_call_table의 4번 원소인 sys_write()가 참조됨
6. ENTRY() 내에서 sys_write()이 호출되어 실제 쓰기 작업 수행

### 리눅스 커널 구성 요소, 영향 초간단 설명

그림은 따로 찾아보기 - 스털링 교재라던가(저작권 issue)

각 컴포넌트가 화살표로 연결된 모습 → 화살표의 시작 부분 컴포넌트가 원인이 되어 끝부분 컴포넌트가 영향을 받았다고 이해

- 유저 컴포넌트 → 커널 컴포넌트 : 시스템 콜이 유일한 방법
- 시스템 콜에서부터 여러 방향으로 화살표 발생
    - 파일 시스템
    - 네트워크
    - 프로세스 등
- 다양한 디바이스 → 인터럽트 발생
- **CPU → Fault**(예외) 발생
