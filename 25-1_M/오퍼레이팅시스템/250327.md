## OS 디자인 이론 - Policy & Mechanism

- **policy**(정책)- OS가 수행할 기능(예: 스케줄링 알고리즘)
- **mechanism**(메커니즘)- OS가 수행하고자 하는 기능을 구현하는 방법
    - 예시 - 하드웨어 측면에서 프로세스 스위치 진행 방식

## 프로세스 관리

OS가 제공하는 근본적인 기능

프로세스를 생성, 스위치(변경), 종료하는 것

프로세스 관리를 통해 제공하고자 하는 가치→ **CPU 가상화**(CPU Virtualization)

- 프로세서가 하나인 경우 한 번에 한 명령어만 실행 가능함
- 이때 time slice를 (사람이 인식하기 힘든)작은 단위로 쪼개게 되면 프로세스 스위치가 일어나서 잠시 중단되더라도 각 프로세스가 연속적으로 실행되는 것처럼 느껴짐
    - 사용자의 프로세스에게 하나의 CPU가 할당된 것처럼 동작하는 Illusion 제공

### 프로세스 관리에 대한 OS의 책임

1. 프로세스를 표현하고 제어할 수 있는 메커니즘 제공
2. CPU의 프로세스 스케줄링 정책 제공

## 스택과 힙

### 스택(Stack)

OS는 각 프로세스(또는 스레드)마다 **Call Stack**(=Runtime Stack, 또는 그냥 스택)을 할당해 실행 시퀀스(실행 순서) 관리

프로시저(함수)는 항상 호출 및 실행되지 않으므로 관련 데이터를 스택에 저장하는 것이 바람직

### [저장되는 정보]

- 지역 변수, 매개 변수
    - 함수가 호출되는 경우에만 변수를 동적으로 할당하기 위해
- 함수 리턴 주소
    - 각 함수 내에서 중첩되어 호출된 함수는 그 역순으로 리턴
    - 위의 호출, 리턴 순서가 스택의 동작 방식(LIFO)과 동일해 스택 이용
- 레지스터 정보

**스택 포인터**: 콜 스택의 top 참조

- call, ret(함수 호출 및 리턴) 명령어가 자동으로 top을 업데이트

> - OS마다 콜 스택과 제어 스택(인터럽트 처리시 이용)이 같을 수도, 다를 수도 있음
> - 우리 교재는 각 프로세스마다 스택이 할당된다고 했으니 제어 스택은 별개로 보는 것 같음
> - [참고] 사실 위 추측의 답은 다음 주 강의에서 등장합니다..

### 힙(Heap)

명시적으로 사용자가 요청한 메모리를 동적 할당하여 저장하는 메모리 공간

윈도우, 리눅스 등의 주류 OS에서는 힙을 지원하지만, 다른 미지원 OS 존재함

→ 힙이 OS의 필수요소는 아님

## 실행 컨텍스트(Execution context)

어느 프로세스 실행시 특정 시점의 CPU의 **모든 레지스터 정보**

- register context라고도 부름

멀티프로세싱에서 프로세스 스위치 진행시 현재 프로세스의 **상태 유지 필요**

- 따라서 각 프로세스 별 실행 컨텍스트가 저장되고 복원되는 체계 필요

## PCB(Process Control Block)

프로세스 관리에 필요한 정보를 저장하는 자료구조

OS가 프로세스 스위칭 할때 PCB 없으면 안 됨

### [포함하는 정보]

- PID
    - 프로세스의 ID(각 프로세스 구분 키 역할)
- PPID
    - 자신을 생성한 프로세스(부모 프로세스)의 PID
- 프로세스 상태
    - READY: 디스패처에게 선택되어 CPU만 할당된다면 언제든 실행 가능한 상태
    - RUNNING: 현재 CPU에 의해 실행 중인 상태
    - BLOCKED: (I/O 인터럽트 대기 등의 이유로) 실행할 수 없는 상태
- PC
- 실행 컨텍스트
- 메모리 포인터
    - PCB의 나머지 요소를 가리키는 포인터
- 그 외 정보
    - 현재 프로세스의 우선 순위
    - I/O 상태 등

프로그램 로딩시 PCB와 스택 추가해 프로세스 생성

> [참고] 유닉스는 C언어 기반 운영체제 → 웬만한 운영체제에서 PCB가 구조체 형식으로 구현됨
>

## 프로세스 이미지(Process Image)

프로세스의 현재 모습을 묘사하는 **스냅샷**

프로세스 구성 요소(코드, 데이터, PCB, 스택)의 현재 상태로 정의됨

**프로세스 생성시 OS는 프로세스 이미지를 생성**

1. 프로그램(코드 + 데이터) 로드
2. 스택 할당 및 초기화
3. PCB 할당 및 초기화

> 종료는 그 역순. 프로세스 종료 후 관련 리소스 해제한 뒤 이미지 구성 요소 제거
>

## 프로세스 리스트

OS가 PCB를 집합 형태로 관리하는 자료구조

- 커널이 관리 → 프로세스 리스트는 커널 부분에 존재

PCB를 한데 모아 관리한다는 데 의미 존재

- 프로세스 테이블: UNIX에서 PCB들을 배열 형태로 관리하던 것
- 프로세스 리스트: 배열 대신 연결 리스트 활용

상태별로 프로세서를 관리

- **ready queue** - 언제든 CPU에 의해 실행될 준비가 된 상태인 PCB의 집합. **스케줄링의 대상**
    - 타이머 인터럽트, CPU 관련 시스템 콜 → 현재 프로세스를 레디 큐에 적재
- **blocked queue** - 이벤트가 발생할 때까지 (대기하느라 ㅜㅜ) **수행할 수 없는**(blocked) PCB의 집합
    - I/O 관련 시스템 콜 → 현재 프로세스를 블럭 큐에 적재
    - I/O 요청이 존재하는 프로세스: 그 다음 명령이 I/O 요청 결과에 의존하는 경우 많아 READY 상태로 변경하면 위험함
- **Current pointer** - **현재 프로세스**를 가리킴

### [프로세스 스위치 과정에서 PCB의 용도]

1. 현재 실행 중인 프로세스의 모든 레지스터 정보 저장
2. 현재 프로세스의 상태를 PCB에 업데이트 → 적절한 큐에 적재
3. 다음에 실행할 프로세스를 선택할 때 참조 → PCB 내 상태 정보를 RUNNING으로 업데이트
4. 선택된 프로세스의 컨텍스트 정보를 CPU에 복원

> 프로세스 스위치≠ 모드 스위치<BR>
> → 이벤트(인터럽트, 익셉션), 시스템 콜 호출 등에 의해 모드 스위치가 발생했을 때 프로세스 스위치가 꼭 진행되진 않음
