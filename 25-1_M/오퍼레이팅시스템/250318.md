## 캐시 쓰기 과정

캐시 읽기와 달리 캐시에 쓴 내용을 메모리에 언제 반영해야 할지 고려해야 함

### Write-Through 방식

캐시에 데이터 쓰기 후 바로 메모리에 변경 내용 반영

메모리의 데이터랑 다를 일이 없어(동기화 문제 X) 메모리와 쓰기 작업을 진행한 프로세서의 캐시에는 문제가 없음

- 하지만 다른 프로세서의 캐시에 변경 내역을 반영하지 않으므로 문제 발생
- 그리고 성능 안 좋아서 현대엔 잘 사용되지 않는 방식

### Write-Back 방식

캐시에 데이터를 쓴 뒤에 바로 반영하지 않고 추후에 반영

근거: 참조의 지역성 

- 쓰기 연산이 얼마 뒤에 또 진행될 확률이 큼

dirty bit: 데이터가 변경되어 메모리와 다른지 알려 주는 1비트

메모리 접근을 최소화해 처리 속도 향상

하지만 다음 상황에서 데이터 동기화 문제 발생 가능(=memory coherence)

- 멀티 프로세서 시스템인 경우
- 입출력 장치가 DMA 방식으로 데이터를 처리하는 경우

> Memory coherence 문제를 해결하기 위해 하드웨어의 도움을 받아야 함(스누핑 프로토콜 등 - OS 범위 아니므로 참고만 하기)
> 

## I/O 모듈(I/O 장치)

컴퓨터와 사람을 잇는 인터페이스

시스템과 입출력 장치 연결할 때 버스 이용

데이터의 이동 단위는 **words**(주로 4, 8비트)

[참고] I/O와 다른 시스템 구성 요소의 차이점 - 성능, 파라미터 성격

## Bus

서로 다른 장치를 연결하며 그 사이에서 메모리의 주소, 데이터, 제어 신호를 운반하는 주체

데이터의 이동 단위는 words(주로 4, 8바이트)

### 버스 브릿지(Bus Bridge)

서로 다른 버스를 연결하는 하드웨어

데이터 수신 하드웨어에 맞는 전기 신호로 변환하는 역할

> 아키텍처의 벤더마다 버스 브릿지의 명칭이 다르며, 인텔 아키텍처의 경우 메모리를 연결하는 브릿지를 north bridge, 나머지를 연결하는 브릿지를 south bridge라고 함
> 

### 버스 아키텍처

시스템 버스(System Bus): 브릿지와 CPU를 연결하는 버스

메모리 버스(Memory Bus): 브릿지와 메인 메모리를 연결하는 버스

입출력 버스(I/O Bus): 브릿지와 입출력 장치(장치 컨트롤러)를 연결하는 버스. 위의 두 버스보다 느린 속도로 작동

## 장치 컨트롤러(Device Controller)

I/O Controller 또는 I/O Adapter라고도 부르는 **하드웨어**

I/O 버스와 각 입출력 장치를 연결하며, 연결된 장치와 통신하는(장치 관리) 역할

각 장치마다 송수신 속도 등의 성질이 다르므로 각 장치에 맞는 다양한 종류의 컨트롤러 존재

- 위치 - 메인보드 위에 있는 경우도 있고, 장치 안에 내장되어 있는 경우도 있음
- 연결 개수 - USB 컨트롤러와 같이 하나의 컨트롤러에 여러 장치를 연결할 수 있음
- 구조 - 컨트롤러의 구조가 복잡한 경우 간단한 CPU 형태를 갖추기도 함

### 컨트롤러의 일반적 구조

- **인터페이스 부분** - 장치 드라이버를 통해 접근할 수 있는 부분
    - 상태 레지스터(status register) - 현재 장치의 상태 정보를 저장
    - 제어 레지스터(control register) - CPU가 장치를 제어하기 위한 정보와 명령 등을 저장
    - 데이터 레지스터(data register) - 입출력 작업에 필요한 데이터(파라미터 등)를 저장
- **내부 구현 부분**
    - 로컬 버퍼 및 메모리
    - 프로세서
    - 각 장치에 필요한 칩들

### 장치 드라이버(Device Driver)

장치 컨트롤러마다 하나씩 존재하는 OS 코드

- CPU와 입출력 장치를 연결하는 소프트웨어 측면의 통로

CPU는 장치 드라이버 통해 컨트롤러와 통신

- 드라이버에  레지스터 확인 및 조작법, 명령어 종류, 전송할 인터럽트 요청 형식 등이 다 정의됨

## Bus Transaction

읽기 및 쓰기 작업 수행에 요구된 일련의 과정

1. Bus Master
    - 버스 트랜잭션 작업을 개시하는 주체
    - CPU, 입출력 장치가 이에 해당
2. Bus Slave
    - 버스 트랜잭션 작업 지시를 받아 수행하는 주체
    - 메모리, 입출력 장치가 이에 해당

### **Bus Arbiter**(버스 중재자)

> 여러 장치가 연결을 공유하는 버스의 동시 접근을 제어하는 하드웨어 부품
> 

버스 또한 자원이므로 버스 사용 전에 버스 사용을 요청해야 함

- 버스 트랜잭션을 위해 마스터가 요청

버스 아비터는 마스터의 요청을 수신한 뒤, 버스 사용을 허가하는(허가 신호 전달) 역할

## 메모리 접근

특정 주소의 메모리 접근은 load, store 명령에 의해 이루어짐

- 해당 명령을 통해 버스 트랜잭션을 개시

### [예시] store to memory

1. CPU가 시스템 버스에 주소 A 전달
2. 버스 브릿지 - 메모리 버스를 거쳐 메모리에 도달한 A를 메모리가 수신
3. 메모리는 주소 A에 저장될 데이터를 기다림
4. CPU가 시스템 버스에 데이터 워드 y 전달
5. 메모리에 도착한 y를 읽고 A에 적재

## 입출력 장치 접근 방식

보통 입출력 명령시 데이터는 워드 단위로 이동하며, 메커니즘상 중간에 CPU의 레지스터를 거침

- [예시: 디스크의 값을 읽는 상황] 메모리에 적재되기 전 CPU의 레지스터(아마 MAR, MBR일 듯)에 값을 저장한 뒤에 메모리에 적재

## Programmed I/O

(= Polling I/O)

I/O 명령 마무리를 위해 CPU가 장치의 입출력 수행 완료 여부를 계속 체크하는 방식

### [예시] 디스크에서 데이터 읽는 과정

> CPU 입장에서 데이터를 읽을 때 결과가 메모리에 있어야 하므로, 사실상 디스크에서 read, 메모리에 write 과정이 한번에 일어남을 염두
> 
1. CPU가 읽기 명령을 개시하면서 디스크에 작업 지시
2. 디스크가 작업 수행 - 로컬 버퍼에 데이터 적재
    - CPU는 수행이 완료될 때까지 장치 컨트롤러의 상태 레지스터를 반복 확인(폴링)
    - 디스크의 적재 작업이 진행되는 동안 CPU는 다른 명령을 처리하지 못함
3. 레지스터 확인 후  CPU가 디스크의 버퍼 내용을 메모리에 적재

Programmed I/O 방식은 입출력 과정에서 CPU가 유용한 작업을 처리하지 못하므로 효율이 좋지 않음

### 2. Interrupt-Driven I/O

> Programmed I/O와 비슷하지만 CPU가 입출력 인터럽트를 통해 작업 완료 여부를 파악한다는 차이점 존재
> 

### [예시] 디스크에서 데이터 읽는 과정

1. CPU가 읽기 명령을 개시하면서 디스크에 작업 지시
2. 디스크가 작업 수행 - 로컬 버퍼에 데이터 적재
    - CPU는 이전에 처리하던 프로세스 등 다른 유용한 일을 진행하며 I/O 인터럽트 대기
    - Programmed I/O 방식처럼 상태 레지스터를 계속 확인하지 않아도 됨
3. 작업 완료 후 인터럽트 발생시 CPU가 인터럽트 핸들러 통해 읽기 명령 마무리

인터럽트를 통해 CPU 활용률이 증가했으나 아직도 CPU의 개입이 많이 이루어짐

### 3. DMA(Direct Memory Access)

> 입출력 과정에서 **CPU 개입을 최소화**하고자 디바이스가 **메모리에 직접 접근**해 작업하는 방식
> 

위의 두 방식은 워드 단위로 작업이 진행되므로 입출력 데이터가 커질 경우 CPU 개입으로 인해 비효율적

- 큰 데이터를 워드 단위로 쪼개 명령의 수가 증가하는 만큼 CPU 개입 시간도 비례해 증가하므로

워드가 아닌 블록 단위 입출력 요청에서 CPU가 각 워드 처리 과정에 개입하지 않아 효율적

- CPU 대신 DMA 컨트롤러가 데이터 처리 과정 수행
    - DMA 컨트롤러는 장치 컨트롤러 내에 존재할 수도 있고, 외부에 분리된 상태로 존재할 수 있음
- 따라서 CPU를 더 효율적으로 이용 가능

### [예시] 디스크에서 데이터 읽는 과정

1. CPU가 디스크 읽기 명령 개시하면 디스크의 컨트롤러가 명령 수신
2. 디스크 컨트롤러에 의해 디스크가 작업 진행
3. 디스크의 버퍼에 저장된 결과를 장치 컨트롤러(정확히는 DMA 컨트롤러)가 메모리에 직접 적재
4. 처리 완료시 장치 컨트롤러가 CPU에 인터럽트 신호 전달해 읽기 명령 마무리

> [참고] 버스라는 공유 자원에 대한 CPU와 DMA 컨트롤러의 경쟁 상태 발생함. 자원 대기로 인해 약간의 성능 하락이 있을 수는 있으나, 이를 감안해도 위의 두 방식보다는 효율적이라고 함. 또한 캐시의 존재, 스케줄링 등으로 성능 하락 약간 커버됨
> 

## I/O 주소 공간

입출력 장치에서 사용하는 주소 체계를 말함

### Port-Mapped I/O

입출력 장치가 **분리된 주소 공간**을 갖는 것

- 메모리 공간으로 사용할 주소와 입출력 장치의 주소(포트)는 별개이므로 주소 자체가 겹쳐도 상관 없음

**Special I/O instructions**

- 입출력 장치에서만 사용하는 특별한 명령어
- 명령어를 통해 해당 읽기/쓰기 명령이 메모리의 명령인지 입출력 장치의 명령인지 판단 가능
    - 브릿지는 명령어를 해석해 데이터를 적절한 버스에 전달

덕분에 주소 자체가 메모리와 겹쳐도 명령어 형식을 통해 구분하면 되므로 문제 없음

하지만 기술이 발전하면서 입출력 장치와 메모리의 명령어를 통일했으면 좋겠다는 의견 대두

### Memory-Mapped I/O

동일한 명령어를 사용하되, 주소의 범위를 통해 해당 명령의 수신자를 결정

주소를 미리 예약해야 함

사용할 수 있는 메모리 주소의 범위가 입출력 장치의 주소 범위만큼 감소 - 공간적 희생

## 멀티 프로세서 시스템

### Asymmetric Multiprocessing(AMP)

각 프로세서의 기능이 다른(비대칭적인) 시스템

- [과거 사례] 한 프로세서는 커널만을 수행(Master), 나머지 프로세서는 애플리케이션만을 수행(Slave)
- 멀티 프로세서 시스템에서 특정 프로세서는 입출력만을 처리하는 경우
    - 이 경우 입출력 버스가 특정 프로세서하고만 연결

### Symmetric Multiprocessing(SMP)

각 프로세서의 기능이 동일한(대칭적인) 시스템

- 각 프로세서가 기능을 가리지 않고 골고루 수행

보통의 범용 컴퓨터가 이 시스템 아키텍처를 채택

메모리 공유 방식을 기준으로 UMA와 NUMA 아키텍처로 구분

### 1. UMA(Uniform Memory Access)

모든 프로세서가 하나의 공유 메모리에 접근하는 아키텍처

메모리 접근 시간이 모든 프로세서에서 동일

프로세서가 많아질수록 메모리 접근 횟수 증가로 인한 병목현상(폰노이만 병목) 발생

### 2. NUMA (Non-Uniform Memory Access)

각 프로세서마다 로컬 메모리가 존재하는 아키텍처

- 다른 로컬 메모리에 접근을 못하는 건 아님

특정 프로세서가 자주 사용하는 데이터를 자신의 로컬 메모리에 배치함으로써 병목 어느정도 해결

- 자주 사용하지 않는 데이터를 자신과 멀리 있는 로컬 메모리에 저장

하지만 NUMA 아키텍처를 지원하기 위해 OS 커널의 복잡도가 증가

- 참조의 지역성에 따른 memory tiering 기술을 구현하는 알고리즘이 복잡함

## 멀티코어 시스템

Multi-core Systems

위의 멀티 프로세서 시스템을 하나의 칩으로 만든 것

- 프로세서 간 통신보다 코어 간 통신속도가 빠름
- 멀티코어 시스템에서의 소비전력이 멀티프로세서 시스템보다 유의미하게 낮음

각 프로세서 역할을 하던 주체를 **코어**라고 함

칩 안에서 코어끼리 공유하는 **공유 캐시** 존재

성능상으로는 멀티프로세서 시스템과 차이가 존재하나 OS 입장에서 시스템을 제어할 때는 큰 차이가 없다고 봄

## APIC(Advanced PIC)

SMP 시스템에서 사용하는 PIC

보통 입출력 장치는 모든 프로세서가 접근 가능(공유 자원)

프로세서 별 로컬 입출력 장치가 필요한 경우도 존재

- 예: 시스템 타이머

인터럽트 시그널을 번호(벡터)로 변환 후 동적으로 프로세서 선택 후 전달

### Local APIC

각 프로세서마다 하나씩 존재하는 로컬 APIC

APIC과 프로세서 사이에서 로컬 I/O와 글로벌 I/O의 인터럽트를 구분하여 프로세서로 전달
